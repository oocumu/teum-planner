# 코드 리뷰 가이드

## 1. 리뷰의 목적
- 버그와 보안 문제를 병합 전에 잡는다.
- 코드를 읽기 쉽고 유지보수하기 쉽게 만든다.
- 팀원 간 지식을 공유한다.

리뷰는 **코드**에 대한 것이지 **사람**에 대한 것이 아닙니다.

## 2. 피드백 태그

모든 리뷰 코멘트는 맨 앞에 태그를 붙여 우선순위를 명확히 합니다.

| 태그 | 의미 | 병합 전 조치 |
| --- | --- | --- |
| **[MUST]** | 반드시 고쳐야 함. 버그, 보안, 요구사항 누락, 컨벤션 위반 | 수정 필수 (Request changes) |
| **[SHOULD]** | 고치는 것을 강하게 권장. 가독성, 구조, 성능 개선 | 수정하거나 안 하는 이유를 답글로 설명 |
| **[COULD]** | 선택 사항. 취향, 작은 개선 아이디어 | 작성자 판단 |
| **[QUESTION]** | 의도를 묻는 질문 | 답글로 답변 |
| **[PRAISE]** | 잘한 점 칭찬 | 없음 |

## 3. 코멘트 작성 형식

```
[태그] 문제 요약 (한 줄)

- 이유: 왜 문제인지
- 제안: 어떻게 바꾸면 좋을지 (가능하면 코드 예시)
```

**예시**
```
[MUST] API 키가 코드에 하드코딩되어 있습니다.

- 이유: 공개 저장소에 올라가면 키가 유출됩니다.
- 제안: `.env`로 옮기고 `.gitignore`에 추가해 주세요.
```

## 4. 리뷰 체크리스트

**기능**
- [ ] PR 설명대로 동작하는가?
- [ ] 예외 상황(빈 입력, 네트워크 오류 등)을 처리하는가?

**보안**
- [ ] 비밀 값(API 키, 토큰)이 코드에 없는가?
- [ ] 사용자 입력을 그대로 HTML에 넣지 않는가? (XSS)

**가독성**
- [ ] 변수·함수 이름이 의도를 드러내는가?
- [ ] 함수가 한 가지 일만 하는가?
- [ ] 중복 코드가 없는가?

**컨벤션**
- [ ] 브랜치 이름, 커밋 메시지, PR 제목이 규칙을 따르는가?

## 5. 리뷰 결과 선택
- **Approve**: [MUST]가 없을 때
- **Request changes**: [MUST]가 하나라도 있을 때
- **Comment**: 질문이나 [SHOULD]/[COULD]만 있을 때

## 6. 작성자 응답 규칙
- 모든 코멘트에 답글을 남긴다. (수정했다면 커밋 해시 첨부: `abc1234에서 수정했습니다`)
- [MUST]는 반드시 반영 후 리뷰어에게 재요청한다.
- 해결된 코멘트는 리뷰어가 **Resolve conversation** 한다.

## 7. 리뷰 매너
- "왜 이렇게 했어요?" 보다 "이 부분은 ~한 이유로 ~하면 어떨까요?"
- 잘한 점도 최소 한 가지는 [PRAISE]로 남긴다.
- 24시간 안에 → 영업일 기준 24시간 안에
